# Implementation decisions

The supplied plan is the design reference. The following are deliberate departures from its initial stack, not claims that the exact plan has been completed.

1. Retain FastAPI/Python for record coordination, extraction and document generation instead of rewriting working code in Go. Measured text processing is already below the plan's 50 ms NLU target; speech dominates latency. Nginx supplies the public gateway and static frontend.
2. Default deployment is three containers: web/gateway, record API, and ASR. Text extraction and document generation run in-process in the API to avoid HTTP overhead on an edge device. Separate stateless NLU and renderer applications are available under the `workers` Compose profile; this profile is an independent worker interface, not automatic API offload.
3. Use a precompiled regex matcher and standard-library normalization rather than spaCy, RapidFuzz and text2num. This keeps cold starts and runtime footprint small. Unknown drug suggestions use difflib, never silent replacement.
4. Use JSON Schema generated from Pydantic plus generated TypeScript definitions and OpenAPI. The frontend uses a small typed fetch helper, not an external generated-client runtime. Contract drift is checked in CI. Go bindings are absent because no Go service is used.
5. Use ReportLab for downloadable PDF and deterministic Python text/HTML templates. `jsonschema` validates the project's FHIR-lite envelope. FHIR-lite is not FHIR R4 conformance; terminology codes are intentionally omitted until validated against their official sources.
6. Use `cryptography` for optional AES-256-GCM encryption of extraction and revision payloads. It does not encrypt metadata, actor names, SQLite pages or existing plaintext rows. Full-disk encryption is still appropriate for device protection. The key is supplied externally and never written to the database.
7. Use psycopg and its bounded connection pool for PostgreSQL deployments. SQLite WAL remains the offline device default. A transactional PostgreSQL advisory lock serializes audit-head allocation across replicas. This preserves chain integrity, but the single chain is deliberately a serialized write boundary.
8. Use a native Vite build plugin to precache the app shell instead of adding a PWA framework. API responses and record data are never cached by the service worker. Offline means local services remain running; an installed shell does not run Python or Whisper inside a browser.
9. Tiny.en is the latency default based on local synthetic benchmarks, not a clinical accuracy assessment. Base.en and the existing small model remain selectable. Weights are provisioned before runtime, copied into the ASR image, and runtime downloads are disabled.
10. Streaming uses mono PCM16 at 16 kHz, an AudioWorklet, 600 ms provisional update windows, an RMS endpoint detector, 700 ms silence finalization, bounded buffering and a single warm inference worker per ASR replica. This is chunked Whisper transcription, not a native token-streaming recognizer. A real VAD model and acoustic tuning may improve difficult environments; measurements must include noisy human recordings.
11. `hypothesis`, `pytest`, `httpx`, `ruff`, Playwright, TypeScript and Prettier are development/verification tools. They do not ship in the frontend runtime bundle or API runtime image. Audio fixtures were synthesized locally with Windows Speech; no cloud TTS or patient data is used.
12. Language is English transcription. Cross-language translation, cloud ingestion, AWS infrastructure, a local LLM, trained ONNX NER, and clinical dose-range validation have not been added. These require separate evidence, datasets, provisioning or validation; cloud processing is not part of the offline runtime.

References consulted for the implementation: [faster-whisper source](https://github.com/SYSTRAN/faster-whisper), [FastAPI WebSockets](https://fastapi.tiangolo.com/advanced/websockets/), [Docker internal networks](https://docs.docker.com/reference/compose-file/networks/), and [Nginx dynamic upstream resolution](https://nginx.org/en/docs/http/ngx_http_upstream_module.html).
